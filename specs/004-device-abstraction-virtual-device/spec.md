# Feature Specification: Device Abstraction and Virtual Device

**Feature Branch**: `004-device-abstraction-virtual-device`

**Created**: 2026-11-14

**Status**: Draft

**Input**: User description: "Device abstraction and virtual device (roadmap item 004): a hardware-independent device abstraction that the application and UI use for every capture device, plus a virtual (simulated) device that is always available so every feature can be tried without capture hardware. The abstraction covers discovery with hot-plug events, declared capabilities that are enforced before anything reaches hardware, configuration, background cancellable acquisition streaming sample chunks into the signal storage core, and first-class failure handling (disconnect, transport errors, overruns keep everything captured so far, record lost samples as gaps, report an actionable error, contain faulty drivers). The virtual device generates signal data itself, is seedable and reproducible, can simulate failures on request, and marks its data as simulated. Real hardware drivers, UI, decoders and the session file format are out of scope."

## Overview

Every capture device in the product — the three mandatory hardware devices now and any
later one — must look the same to the rest of the application. This feature defines that
common contract and delivers the first device that implements it: a virtual device that
needs no hardware. Its "users" are the developers of the UI, decoders and session
features, the authors of the hardware drivers that come next (roadmap items 011–013),
and, indirectly, end users who want to try the product without a device and who need to
trust that a failing device never costs them data.

Terms used in this document:

- **Device**: something that can capture digital signals — a hardware analyzer or the
  virtual device.
- **Capabilities**: what a device declares it can do: channel count, supported sample
  rates, trigger types, buffer depth.
- **Configuration**: the user's choices for one acquisition: enabled channels, sample
  rate, trigger, how much to capture.
- **Acquisition**: one run of a device, from start until it finishes, is stopped, or
  fails; its samples flow into a capture in the signal storage core.
- **Simulated**: data that was generated by the virtual device and is not a real
  measurement.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Discover and select devices (Priority: P1)

The application asks which capture devices are available and receives a list that always
contains the virtual device, plus every connected hardware device, each with a stable
identity, a human-readable name, whether it is simulated, and its declared capabilities.
The user can pick any of them in the same way.

**Why this priority**: nothing else can happen until a device can be found and chosen;
the always-present virtual device lets every later feature be exercised without hardware.

**Independent Test**: with no hardware attached, list the devices and confirm the virtual
device is present with complete capabilities; add a test device and confirm it appears
in the list in the same shape.

**Acceptance Scenarios**:

1. **Given** no hardware is connected, **When** devices are listed, **Then** the list
   contains exactly the virtual device, marked as simulated, with its capabilities.
2. **Given** a hardware device is connected, **When** devices are listed, **Then** it
   appears with a stable identity, a name, `simulated = false` and its capabilities.
3. **Given** the same device is listed twice, **When** the identities are compared,
   **Then** they are equal, so a selection survives a refresh of the list.
4. **Given** the list is requested while a device is misbehaving or being unplugged,
   **When** it is produced, **Then** it still returns promptly with the healthy devices
   and never blocks the caller.

---

### User Story 2 - Configure within declared capabilities (Priority: P1)

The user configures an acquisition: which channels, which sample rate, which trigger and
how much to capture. The configuration is checked against the device's declared
capabilities before it can reach the device. Anything the device cannot do is rejected
with a clear, actionable error; an acceptable configuration is applied exactly as given
or the rejection says why not.

**Why this priority**: the constitution requires invalid configuration to be rejected
before it reaches hardware, so a wrong setting can never put a device in an undefined
state.

**Independent Test**: for a device with known capabilities, apply a table of valid and
invalid configurations and confirm each invalid one is rejected with the expected error
before any call is made to the device, and each valid one is accepted.

**Acceptance Scenarios**:

1. **Given** a device supporting 8 channels, **When** a configuration enables channel 8
   (the ninth), **Then** it is rejected with an error naming the channel and the limit.
2. **Given** a sample rate the device does not support, **When** the configuration is
   applied, **Then** it is rejected, and the error lists the supported rates or the
   nearest supported one.
3. **Given** a trigger type the device does not declare, **When** applied, **Then** it
   is rejected naming the supported trigger types.
4. **Given** a capture length larger than the device's buffer depth allows for the chosen
   channels and rate, **When** applied, **Then** it is rejected or clearly limited,
   never silently truncated.
5. **Given** an invalid configuration, **When** it is rejected, **Then** the device
   itself received no call at all (verified with a counting test device).
6. **Given** a valid configuration, **When** it is applied, **Then** the device can
   report back the configuration it will actually use.

---

### User Story 3 - Run a capture into the signal store, in the background (Priority: P1)

The user starts an acquisition. Samples flow in the background from the device into a
capture in the signal storage core; the caller (the UI) is never blocked. Progress is
observable while it runs, the user can stop it at any moment, and when it ends the
capture contains every sample that was delivered, closed and ready to use.

**Why this priority**: this is the product's core flow; it joins devices to storage and
proves the whole path works with the virtual device.

**Independent Test**: start an acquisition on the virtual device, watch progress while
reading the growing capture from another thread, stop it, and confirm the capture holds
exactly the samples produced and every call returned immediately.

**Acceptance Scenarios**:

1. **Given** a configured device, **When** the acquisition starts, **Then** the call
   returns immediately and samples start to arrive in the capture.
2. **Given** a running acquisition, **When** the capture is read from another thread,
   **Then** readers see consistent data and progress (samples captured so far) is
   available.
3. **Given** a running acquisition, **When** the user requests a stop, **Then** the
   device stops within a short, documented time, the capture is closed, and everything
   delivered before the stop is kept.
4. **Given** an acquisition with a fixed capture length, **When** the length is reached,
   **Then** the acquisition finishes by itself and the capture is closed and complete.
5. **Given** the storage memory budget is reached during an acquisition, **When**
   appending stops, **Then** the acquisition ends cleanly with a clear error, the data
   already stored stays intact and readable, and the capture is flagged incomplete.
6. **Given** an acquisition is already running on a device, **When** another start is
   requested for the same device, **Then** it is rejected with a typed error.
7. **Given** two different devices, **When** both run acquisitions, **Then** they run
   independently and one's failure does not affect the other.

---

### User Story 4 - Failures keep data and are never silent (Priority: P1)

When a device is unplugged, the transport fails, or the device reports a buffer overrun,
everything captured so far is kept, the lost range is recorded as a gap, the capture is
flagged incomplete, and the user receives an actionable error. A faulty driver — one that
returns errors, hangs or even panics — is contained: it cannot take down the application,
other devices or the session.

**Why this priority**: the primary goal of the project is a program that does not crash
and does not lose data; failures of external hardware are the most likely way to lose a
capture.

**Independent Test**: with a test device that can be told to fail in each way (disconnect,
transport error, overrun, panic, hang), run acquisitions and confirm in every case that
the samples delivered before the failure are intact, the loss is recorded exactly, the
capture is incomplete, the error is reported, and the application keeps running.

**Acceptance Scenarios**:

1. **Given** a running acquisition, **When** the device disappears, **Then** the
   acquisition ends with a "device disconnected" error, the data before the disconnect
   is intact, and the capture is closed and flagged incomplete.
2. **Given** a running acquisition, **When** the transport reports an error, **Then** the
   error is reported with a user-actionable message and technical detail for the log,
   and the capture keeps all earlier data.
3. **Given** the device reports that N samples were lost, **When** the report arrives,
   **Then** a gap of exactly N positions is recorded at the right place, the capture is
   flagged incomplete, acquisition continues if the device can, and the loss count equals
   what the device reported.
4. **Given** a driver that panics while acquiring, **When** the panic happens, **Then** it
   is contained at the acquisition's worker, logged, reported as a failure of that
   acquisition, and the application and other devices are unaffected.
5. **Given** a driver that stops responding during stop or start, **When** the caller
   requests a stop, **Then** the caller is not blocked: it gets a timeout error within a
   documented time and the capture is closed with what it has.
6. **Given** any failure, **When** the capture is inspected afterwards, **Then** the number
   of samples stored plus the number of positions recorded as lost equals the number of
   positions the device accounted for (nothing disappears unaccounted).

---

### User Story 5 - A reproducible, clearly labelled virtual device (Priority: P1)

The virtual device generates signal data itself, according to its configuration. With the
same seed and configuration it produces exactly the same signals every time. Everything it
produces is marked as simulated wherever the capture is described, so it can never be
mistaken for a real measurement.

**Why this priority**: it lets users and developers try every feature without hardware and
gives all later tests a deterministic data source; the label protects the integrity of
real measurements.

**Independent Test**: run the virtual device many times with the same seed and
configuration and confirm the captured samples are identical; change the seed and confirm
they differ; confirm the capture description says the data is simulated.

**Acceptance Scenarios**:

1. **Given** a seed and configuration, **When** two acquisitions run to a fixed length,
   **Then** their samples are identical.
2. **Given** different seeds, **When** acquisitions run, **Then** their samples differ.
3. **Given** an acquisition on the virtual device, **When** the capture is described,
   **Then** it states the data is simulated, which device produced it and which seed was
   used.
4. **Given** no signal source is configured, **When** it runs, **Then** it produces
   generic random digital signals on the enabled channels.
5. **Given** a configured signal source supplied by a later feature (for example a
   protocol decoder's generator), **When** the virtual device runs, **Then** it asks that
   source for the samples and delivers them through the same path, so such data decodes
   correctly later.
6. **Given** a real device and the virtual device, **When** their captures are described,
   **Then** only the virtual one carries the simulated mark and the mark cannot be
   removed by the consumer.

---

### User Story 6 - Simulate failures and triggers on demand (Priority: P2)

A developer or tester can ask the virtual device to fail on purpose: lose samples at a
given point, overrun, disconnect, return a transport error. The virtual device can also
honour simple triggers so the trigger path of the abstraction is exercised end to end.

**Why this priority**: it makes the failure behaviour of User Story 4 testable and
demonstrable without breaking real hardware; triggers beyond declaring them are not needed
for the first release.

**Independent Test**: instruct the virtual device to lose 1,000 samples after 50,000;
confirm the capture contains a gap of exactly that size at exactly that position and is
flagged incomplete; repeat for the other failure kinds and for an edge trigger.

**Acceptance Scenarios**:

1. **Given** a request to lose N samples at position P, **When** the acquisition runs,
   **Then** a gap of N positions starts exactly at P.
2. **Given** a request to disconnect after a number of samples, **When** the acquisition
   runs, **Then** it fails as a real disconnect would.
3. **Given** a request for a transport error or an overrun, **When** it runs, **Then** the
   corresponding failure path is taken.
4. **Given** a simple level or edge trigger on one channel, **When** the acquisition
   starts, **Then** capturing begins at the trigger position, which is reported.
5. **Given** failure simulation is not requested, **When** the device runs, **Then** it
   never fails on its own.

---

### User Story 7 - Hot-plug awareness (Priority: P2)

While the application runs, the application learns when a hardware device appears or
disappears, so the device list can be kept current. A device that disappears during an
acquisition is handled as in User Story 4.

**Why this priority**: it improves the experience but the product works with an explicit
refresh of the list.

**Independent Test**: with a test hot-plug source, add and remove a device while the
application runs and confirm a matching event arrives for each and the list reflects it.

**Acceptance Scenarios**:

1. **Given** the application is running, **When** a device is connected, **Then** a
   "device appeared" event with the device's description is delivered.
2. **Given** a device is listed, **When** it is removed, **Then** a "device disappeared"
   event with its identity is delivered and it leaves the list.
3. **Given** the virtual device, **When** the list changes, **Then** the virtual device is
   never reported as disappearing.
4. **Given** several devices appear and disappear quickly, **When** events are consumed,
   **Then** none is lost or duplicated and their order is preserved.

---

### User Story 8 - Cheap to add a new driver, testable without hardware (Priority: P2)

A developer adding a driver for a real device implements only the device contract and can
test it completely without the hardware, using recorded device traffic or a simulated
device in a ready-made test harness that replays data and injects failures.

**Why this priority**: the three mandatory drivers (roadmap items 011–013) each need
hardware-free tests; making that cheap keeps drivers independent and well tested.

**Independent Test**: write a minimal test driver using only the harness, replay a
recorded session through it, and confirm it passes the same acquisition and failure tests
as the virtual device.

**Acceptance Scenarios**:

1. **Given** a recording of device traffic, **When** the harness replays it to a driver
   under test, **Then** the driver's samples, gaps and errors can be compared with the
   expected ones.
2. **Given** the harness, **When** it is told to inject a disconnect, a short read or a
   timeout at a point of the recording, **Then** the driver under test sees exactly that.
3. **Given** a driver under test, **When** the shared conformance tests are run against
   it, **Then** they check discovery, capability enforcement, start/stop, failure
   handling and panic containment with no hardware.
4. **Given** a new driver, **When** it is added, **Then** it does not change the behaviour
   of any existing driver or of the virtual device.

---

### Edge Cases

- Start requested on a device that was unplugged since the list was made.
- Start, stop or configure requested in the wrong state (stop while idle, configure while
  running): each gives a typed error and changes nothing.
- A device whose capabilities change between listings (for example a firmware variant):
  the configuration is validated against the capabilities of the device actually in use.
- Requested sample rate not exactly achievable by the device: rejected or the actual rate
  is reported before the acquisition starts, never silently different.
- A device delivers chunks larger than the storage accepts in one step, or faster than the
  store can ingest: chunks are split, or the excess is recorded as a gap, never dropped
  silently.
- The consumer of progress/events is slow or gone: the acquisition is not slowed or
  blocked by it.
- Two acquisitions started at almost the same moment on the same device: exactly one
  starts.
- Acquisition finishes at the same moment the user presses stop: the capture ends closed
  with a defined result either way.
- Disconnect during start-up, during stop, or immediately after a loss report.
- A device claims a channel count or buffer depth that is inconsistent or zero:
  the device description is rejected as invalid instead of being listed.
- Driver hangs forever: the acquisition is abandoned after a timeout, its worker is
  detached, and the application stays responsive.
- The capture is read while the acquisition fails: readers see a consistent snapshot that
  includes everything delivered before the failure.
- The virtual device is configured with a seed of 0 or the maximum value; with all or one
  channel enabled.

## Requirements *(mandatory)*

### Functional Requirements

**Discovery and identity**

- **FR-001**: The system MUST provide an operation that lists the available capture
  devices; the list MUST always contain the virtual device and every connected hardware
  device.
- **FR-002**: Every listed device MUST have a stable identity that is equal across
  listings and across a reconnect of the same physical device, a human-readable name, a
  flag telling whether it is simulated, and its declared capabilities.
- **FR-003**: Listing MUST NOT block on a misbehaving device; an unresponsive or invalid
  device is omitted (and reported in the log) while the healthy ones are returned.
- **FR-004**: The system MUST deliver "device appeared" and "device disappeared" events
  for hardware devices while the application runs, without losing, duplicating or
  reordering them; the virtual device never disappears.

**Capabilities and configuration**

- **FR-005**: Every device MUST declare its capabilities: channel count, supported
  sample rates, supported trigger types and buffer depth; a device whose declaration is
  inconsistent (for example zero channels) MUST be rejected as invalid.
- **FR-006**: A configuration MUST be validated against the capabilities of the device
  before it reaches the device; an invalid configuration MUST be rejected with a typed
  error that names what is wrong and what is allowed, and the device MUST NOT receive any
  call for it.
- **FR-007**: The validation MUST cover at least: enabled channels exist, sample rate is
  supported, trigger type is supported and refers to an enabled channel, the capture
  length fits the buffer depth where the device requires it, and the memory needed fits
  the storage memory budget.
- **FR-008**: After a valid configuration is applied, the system MUST be able to report
  the configuration the device will actually use (for example the actual sample rate).

**Acquisition**

- **FR-009**: Starting an acquisition MUST return immediately; all device I/O MUST run in
  the background and MUST NOT block the caller (the UI thread).
- **FR-010**: Samples MUST flow from the device into a capture of the signal storage core
  as chunks, using the capture's rules (chunk order, chunk size, memory budget).
- **FR-011**: The caller MUST be able to observe progress (samples captured so far, state)
  and receive completion and failure notifications without polling the device.
- **FR-012**: The caller MUST be able to stop an acquisition at any time; the stop MUST
  take effect within a documented time, close the capture and keep everything delivered.
- **FR-013**: An acquisition MUST be able to finish by itself when a configured capture
  length is reached; the capture is then closed and, if nothing was lost, complete.
- **FR-014**: At most one acquisition runs per device at a time; a second start MUST be
  rejected with a typed error. Acquisitions on different devices MUST be independent.
- **FR-015**: Operations in the wrong state (stop while idle, configure while running,
  start without a valid configuration) MUST return typed errors and change nothing.
- **FR-016**: The acquisition's progress and event consumers MUST NOT be able to slow or
  block the acquisition.

**Failure handling**

- **FR-017**: On device disconnect, transport error or any driver error, the acquisition
  MUST end, the capture MUST keep everything delivered before the failure, be closed and
  be flagged incomplete.
- **FR-018**: When a device reports lost samples (for example an overrun), a gap of
  exactly that many positions MUST be recorded at the right position; the acquisition
  MAY continue if the device can; the capture MUST be flagged incomplete.
- **FR-019**: For every acquisition, the samples stored plus the positions recorded as
  lost MUST equal the positions the device accounted for; nothing may disappear
  unaccounted.
- **FR-020**: Every failure MUST be reported to the user as a typed error with a stable
  code, an actionable explanation and technical detail for the log; failures MUST be
  logged with metadata only, never signal data.
- **FR-021**: A driver that returns an error, panics, or stops responding MUST be
  contained: the panic is caught at the acquisition's worker boundary and reported as a
  failure of that acquisition; a hang yields a timeout instead of blocking the caller;
  other devices, other acquisitions and the application are unaffected.
- **FR-022**: If the storage memory budget is reached during an acquisition, the
  acquisition MUST end cleanly with a typed error, with the stored data intact and the
  capture flagged incomplete.

**Virtual device**

- **FR-023**: The virtual device MUST be available on every supported platform without
  any external requirement and MUST be selectable exactly like a hardware device.
- **FR-024**: The virtual device MUST generate its own signal data according to its
  configuration; with no signal source configured it MUST generate generic random
  digital signals on the enabled channels.
- **FR-025**: The virtual device MUST be reproducible: the same seed and configuration
  MUST give identical samples; a different seed MUST give different samples.
- **FR-026**: The system MUST define a signal-source hook through which later features
  (protocol decoders and their generators) supply the samples the virtual device
  delivers, without changes to the virtual device or the acquisition path.
- **FR-027**: Every capture produced by the virtual device MUST be marked as simulated
  in the capture's description, together with the device identity and the seed; a
  consumer MUST NOT be able to clear that mark, and real devices MUST NOT carry it.
- **FR-028**: On request the virtual device MUST simulate failures — lost samples at a
  chosen position and size, an overrun, a transport error, a disconnect after a chosen
  number of samples — and MUST never fail on its own when not asked to.
- **FR-029**: The virtual device MUST implement simple level and edge triggers on one
  channel, so the trigger path is exercised end to end, and MUST report the trigger
  position.
- **FR-030**: The virtual device MUST support running as fast as possible (for tests)
  and, optionally, paced to the configured sample rate in real time.

**Extensibility and testing**

- **FR-031**: A new device driver MUST require implementing only the device contract;
  adding one MUST NOT change the behaviour of any other driver or of the virtual device.
- **FR-032**: The repository MUST provide a hardware-free test harness that replays
  recorded device traffic to a driver, injects failures (disconnect, short read, timeout,
  panic, hang) at chosen points, and a set of shared conformance tests that any driver
  can run.
- **FR-033**: The device contract and the acquisition behaviour MUST be documented in
  English, including the error codes, the state machine, the stop-time guarantees and the
  semantics of lost samples.

### Key Entities

- **Device**: identity, name, simulated flag, capabilities, availability.
- **Capabilities**: channel count, supported sample rates, supported trigger types,
  buffer depth.
- **Configuration**: enabled channels, sample rate, trigger, capture length, and (virtual
  device only) seed, signal source and failure simulation.
- **Acquisition**: one run of a device with a state (idle, configured, running, stopping,
  finished, failed), progress and an outcome; owns a capture while it runs.
- **Acquisition event**: started, progress, gap recorded, finished, failed, stopped.
- **Device event**: appeared, disappeared.
- **Capture description**: device identity and name, simulated flag, seed, configured and
  actual sample rate, channel count, trigger position.
- **Signal source**: the hook that supplies samples to the virtual device.
- **Failure report**: stable code, actionable message, technical detail.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: With no hardware attached, a user can list devices, pick the virtual device,
  configure, capture and view data in 100% of tested runs.
- **SC-002**: In 100% of tested invalid configurations, the configuration is rejected
  before the device receives any call (verified by a call-counting test device); at least
  30 distinct invalid cases are covered.
- **SC-003**: Every operation that the UI may call (list, configure, start, stop, read
  progress) returns within 10 milliseconds, regardless of device behaviour, including a
  device that hangs.
- **SC-004**: A requested stop takes effect and closes the capture within 100 milliseconds
  on the virtual device, and within the documented bound for any driver; the caller is
  never blocked longer than the documented timeout.
- **SC-005**: In 100% of tested failure scenarios (disconnect, transport error, overrun,
  driver panic, driver hang) the data delivered before the failure reads back exactly, the
  capture is flagged incomplete, the application keeps running, and a typed error is
  reported.
- **SC-006**: In 100% of tested scenarios, samples stored plus positions recorded as lost
  equals the positions the device accounted for.
- **SC-007**: 1,000 injected driver panics across varied points of an acquisition never
  crash the application or lose previously delivered data.
- **SC-008**: Running the virtual device with the same seed and configuration 100 times
  gives byte-identical captures; different seeds give different captures.
- **SC-009**: 100% of captures produced by the virtual device are marked simulated and
  100% of captures from other devices are not.
- **SC-010**: The virtual device keeps pace with the signal storage core: acquiring a
  sparse 32-channel signal as fast as possible sustains at least 100 million samples per
  second on the reference machine without recorded losses.
- **SC-011**: A new test driver can be exercised against the full shared conformance suite
  using only the harness, with no hardware, and a replayed recording reproduces the same
  samples, gaps and errors on every run.
- **SC-012**: A hot-plug sequence of 100 rapid connect/disconnect events delivers exactly
  100 events in order, none lost or duplicated.

## Assumptions

- The signal storage core (roadmap item 002) is the destination of all samples: chunks of
  32-bit words, gaps for lost positions, a memory budget; it has no capture-description
  fields yet, so the capture description (including the simulated mark) is kept alongside
  the capture by the acquisition and persisted later by the session file format (roadmap
  item 003).
- Channels are digital and at most 32 per device; analog data is out of scope.
- Real hardware drivers (WeAct, Logic16 clone, Pico) are separate items (011–013); this
  feature only guarantees that adding them is cheap and testable without hardware.
- No user interface exists yet; progress and events are delivered through a programmatic
  interface that the UI will use later.
- Trigger semantics are intentionally minimal (level and edge on one channel); richer
  triggering is a later feature. Devices declare which trigger types they support.
- Hot-plug detection for real devices depends on OS facilities; this feature defines the
  event contract and verifies it with a test source, real detection arrives with each
  driver.
- The virtual device's default mode is as fast as possible; real-time pacing is an option.
- One acquisition per device at a time; several devices may run concurrently.
- The reference machine for performance targets is the maintainer machine recorded with
  the existing benchmark baseline.
- Uses the typed errors and logging of roadmap item 001, the worker panic containment
  from item 001 and the signal storage core of item 002.
