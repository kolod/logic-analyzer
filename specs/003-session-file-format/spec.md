# Feature Specification: Session File Format

**Feature Branch**: `003-session-file-format`

**Created**: 2026-11-14

**Status**: Draft

**Input**: User description: "003 (roadmap item 003, `003-session-file-format`): atomic write and safe read of the native session format, validation, fuzzing, 'simulated' flag. Sigrok `.sr` import/export is a later, separate item."

## Overview

A capture is often a rare, unrepeatable event, so the product must be able to keep it
on disk and bring it back exactly, and a file must never cost the user a capture — not
when the disk is full, not when the power fails in the middle of a save, not when a file
was damaged or crafted to attack the program. This feature defines the product's own
session file: what it stores, how it is written without ever damaging an existing file,
and how it is read back with every byte treated as untrusted.

Its "users" are the developers of the UI (open, save, save as, close with unsaved data),
of the decoders and annotations that will add their own data to a session later (roadmap
items 007–010), of the importers and exporters that come after (`.sr`, CSV), and,
indirectly, end users who need to trust that a saved capture is the capture they took —
including whether it is real or simulated, and whether it is complete.

Terms used in this document:

- **Session**: what one session file holds: one capture with its description, plus
  optional extra sections that later features add.
- **Capture**: the recorded signals of one acquisition, as stored by the signal storage
  core (roadmap item 002): channels, sample rate, transitions, gaps and status.
- **Capture description**: the metadata of the acquisition that produced the capture:
  device identity and name, whether the data is simulated, the seed of the virtual
  device, requested and applied sample rate, enabled channels, trigger, samples skipped
  before the trigger, and the start time (roadmap item 004).
- **Section**: a self-contained, individually checked part of a session file. The
  capture and its description are required sections; decoder settings, annotations and
  view state will be optional sections.
- **Simulated**: data that was generated by the virtual device and is not a real
  measurement.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Save a capture and load it back unchanged (Priority: P1)

A developer (and later the user) saves a capture to a file and loads that file again,
possibly on another machine or another operating system, and gets exactly the capture
that was saved: every channel's levels at every position, every gap, the sample rate,
the status and the capture description.

**Why this priority**: this is the purpose of the feature; without a faithful round trip
nothing else about the format matters.

**Independent Test**: build captures with a known content (random signals, empty
captures, captures with gaps, captures at the limits of the storage core), save each,
load it back, and compare every query the storage core offers on the original and on the
loaded capture.

**Acceptance Scenarios**:

1. **Given** a closed capture with several channels, **When** it is saved and loaded,
   **Then** every level, transition, gap, the length, the sample rate and the status of
   the loaded capture equal the original's.
2. **Given** a capture description with a device name in any language, a seed, a trigger
   and a start time, **When** the session is saved and loaded, **Then** every field is
   equal, including the exact text and the time.
3. **Given** the same capture and description saved twice, **When** the two files are
   compared, **Then** they are byte for byte identical, and also identical when saved on
   Windows and on Debian.
4. **Given** an empty capture (no samples), a capture with one sample, and a capture with
   the maximum number of channels, **When** each is saved and loaded, **Then** each
   comes back unchanged.
5. **Given** a large capture, **When** it is saved and loaded, **Then** the file size
   grows with the number of level changes, not with the number of samples, and loading
   needs no more memory than the capture itself would need.

### User Story 2 - Saving never damages or loses data (Priority: P1)

Saving over an existing file, or creating a new one, either completes entirely or leaves
things exactly as they were. A crash, a power failure, a full disk, a missing
permission, a disconnected drive or a second program holding the file open never
produces a half-written file in place of a good one.

**Why this priority**: the constitution makes data integrity non-negotiable and requires
atomic writes; a save that can destroy the previous good file is worse than no save.

**Independent Test**: save over an existing good file while injecting a failure at every
step of the write (including the end of the disk, a refused rename and a killed process),
and confirm after each that the old file is intact and loadable, that no partial file
carries the target's name, and that the error is typed and actionable.

**Acceptance Scenarios**:

1. **Given** a good file exists, **When** a save to the same path fails at any point,
   **Then** the old file is unchanged and loads as before.
2. **Given** a save is interrupted by killing the process at a random moment, **When**
   the target path is examined afterwards, **Then** it holds either the complete old
   content or the complete new content, never a mixture or a truncated file.
3. **Given** the disk is full or the directory is read-only, **When** a save is
   attempted, **Then** the user gets a typed error that says what to do (free space,
   choose another location) and no temporary leftovers stay behind.
4. **Given** a previous save was killed and left a temporary file, **When** a later save
   to the same path runs, **Then** it succeeds and does not trip over the leftover.
5. **Given** a path that is not valid (empty, a directory, not writable, too long for
   the platform), **When** a save is attempted, **Then** it fails at once with a typed
   error and touches nothing.
6. **Given** a successful save, **When** the call returns, **Then** the data has been
   flushed to storage, so a power failure right after cannot lose it.

### User Story 3 - Loading rejects corrupt and hostile files safely (Priority: P1)

Opening a file never crashes the program, hangs it, or exhausts its memory, whatever the
file contains: a truncated file, a flipped bit, random bytes, a file of another format,
a file that claims absurd sizes, or a file crafted to attack the loader. The result is a
clear typed error that says what is wrong (not a session file, damaged, too new, too big
for the memory budget), or a correct session.

**Why this priority**: files come from outside and may be damaged by disks, transfers or
attackers; the constitution requires loaders to validate everything and to be fuzzed.

**Independent Test**: feed the loader truncations at every length, single-bit flips at
every position, random and structured garbage, files that declare huge counts and sizes,
and a continuous fuzzing run; confirm every outcome is a typed error or a session that
passes the storage core's own consistency checks, and that no case panics, hangs or
allocates more than the configured budget.

**Acceptance Scenarios**:

1. **Given** a valid file cut at every possible length, **When** each is loaded, **Then**
   each fails with a typed "truncated or damaged" error.
2. **Given** a valid file with any single bit changed, **When** it is loaded, **Then** the
   damage is detected (a typed error) — a damaged file is never loaded as if it were
   good.
3. **Given** a file that is not a session file (another format, empty, random bytes),
   **When** it is loaded, **Then** the error says it is not a session file.
4. **Given** a file that declares more channels, samples, transitions, gaps or text than
   the limits allow, **When** it is loaded, **Then** it is rejected before any large
   allocation, with an error that names what exceeded which limit.
5. **Given** a file whose content is well-formed but inconsistent (transitions out of
   order, a gap past the end, a channel count that disagrees with the description),
   **When** it is loaded, **Then** it is rejected with a typed error, never accepted.
6. **Given** a file larger than the memory budget would allow once loaded, **When** it is
   loaded, **Then** it fails with a typed memory-budget error and the application keeps
   its current session.
7. **Given** a continuous fuzzing run of at least one million inputs, **When** it
   finishes, **Then** there were no panics, no hangs and no allocation beyond the budget.

### User Story 4 - "Simulated" and "incomplete" survive the file (Priority: P2)

A capture from the virtual device stays marked as simulated for the rest of its life, and
a capture that is incomplete (samples were lost, a device failed, the memory limit ended
it) stays marked incomplete. Neither mark can be lost by saving, loading, saving again,
or by editing the file.

**Why this priority**: the constitution requires simulated data to be labelled in saved
captures so it can never be mistaken for a real measurement, and incomplete captures to
be never silently valid; the file is where such a label would most easily be lost.

**Independent Test**: save simulated, incomplete and clean captures, load and re-save them
several times, and confirm the marks are unchanged; change the mark inside a file and
confirm the change is detected as damage.

**Acceptance Scenarios**:

1. **Given** a capture from the virtual device, **When** it is saved, loaded and saved
   again, **Then** it is still marked simulated, and its seed is preserved.
2. **Given** a capture from a hardware device, **When** it is saved and loaded, **Then**
   it is not marked simulated.
3. **Given** an interrupted capture with gaps, **When** it is saved and loaded, **Then** it
   is still incomplete, with the same gaps and the same reason (lost samples, device
   failure, memory limit).
4. **Given** a file in which the simulated mark or the completeness mark was edited,
   **When** it is loaded, **Then** the edit is detected and the file is rejected.
5. **Given** a loaded session, **When** a consumer asks for the description, **Then** there
   is no way to clear the simulated mark on it.

---

### User Story 5 - The format can grow without breaking files (Priority: P2)

Later features (decoder settings, annotations, view state, imported metadata) add their
own sections to the session. A program that does not know a section can still open the
file and keep the section when it saves again, an older program refuses a file that needs
something it does not understand with a clear message instead of misreading it, and files
written by this version stay loadable by every later version.

**Why this priority**: sessions written today must stay readable for as long as the
product exists, and the decoder items must be able to extend the file without redoing
this one.

**Independent Test**: load a file that contains an optional section this version does not
know and confirm it opens, keeps the section on re-save, and still passes its checks;
load a file whose format version is newer than supported, or that marks an unknown
section as required, and confirm a clear typed error; keep a set of files written by
every released version as fixtures that must always load.

**Acceptance Scenarios**:

1. **Given** a file with an unknown optional section, **When** it is loaded and saved
   again, **Then** the section is preserved unchanged.
2. **Given** a file with an unknown section that is marked required, **When** it is
   loaded, **Then** it is rejected with an error that says a newer version of the
   program is needed.
3. **Given** a file with a newer major format version, **When** it is loaded, **Then** the
   error names the version found and the versions supported.
4. **Given** the fixture files committed with this version, **When** any later version of
   the code loads them, **Then** they load to the expected content (checked by a test that
   stays in the repository).
5. **Given** two optional sections with the same identifier, or a section with an invalid
   identifier, **When** the file is loaded, **Then** it is rejected as damaged.

---

### User Story 6 - Saving and loading never block the application (Priority: P2)

Saving a large capture, or loading one, runs in the background: the caller gets progress,
can cancel, and is never blocked. A capture that is still being recorded can be saved at
that moment; the file then holds what had been recorded up to that point, marked
incomplete, and the recording is not disturbed.

**Why this priority**: the UI must never freeze (constitution), captures can be large, and
saving a running capture is the building block for protecting data during recording.

**Independent Test**: start a save and a load of a large capture, observe progress, cancel
midway and confirm nothing was left behind and the original file is untouched; save while
an acquisition from the virtual device is running and confirm the recording continues and
the file is a valid, incomplete session.

**Acceptance Scenarios**:

1. **Given** a large capture, **When** a save is started, **Then** the call returns at
   once and progress can be observed until it finishes.
2. **Given** a save or load in progress, **When** it is cancelled, **Then** it stops
   promptly, reports that it was cancelled, leaves any existing target file untouched
   and leaves no temporary file.
3. **Given** a capture that is still recording, **When** it is saved, **Then** the file
   contains a consistent prefix of the data recorded so far, is marked incomplete, and the
   recording continues undisturbed and unchanged.
4. **Given** a background save that fails, **When** its outcome is read, **Then** it is the
   same typed error a blocking save would have returned.
5. **Given** a save and a load running in the background, **When** one worker fails
   internally, **Then** the failure is contained: a typed error is reported and the
   application and the capture in memory are unaffected.

### Edge Cases

- A path with non-ASCII characters, spaces, or the maximum path length of the platform;
  a path on a network drive that disappears mid-save.
- A save to a path that is currently open in another instance of the program: the last
  completed save wins whole; the two never mix.
- Two saves to the same path from the same process at the same time.
- A file that is valid but larger than the user's memory budget (typed error, current
  session kept), and a budget that changed between two loads.
- A capture with the maximum number of transitions on every channel, and a capture with
  none.
- Device names, notes and other text that are very long, empty, contain control
  characters, unpaired surrogates (from the operating system), or text that is not valid
  UTF-8 in a damaged file.
- A start time before 1970 or far in the future, and a clock that went backwards.
- A file whose size changes while it is being read (another program appending to it).
- A file with correct structure but a section whose checksum is wrong, and a file whose
  checksum is right but whose content is inconsistent.
- A directory with many leftover temporary files from earlier crashed saves.
- Saving when the file system does not support atomic rename over an existing file: the
  failure is reported, never worked around by a non-atomic write.
- Loading the same file twice at once.
- A saved file that is opened on a machine with a different byte order or word size: the
  result is identical.

## Requirements *(mandatory)*

### Functional Requirements

**Content and round trip**

- **FR-001**: The system MUST save one capture and its capture description into a
  session file, and load them back such that every query of the storage core (level at a
  position, transitions in a range, gaps, length, sample rate, channel count, status)
  gives the same answer on the loaded capture as on the original.
- **FR-002**: The system MUST store the capture description completely: device
  identity, device name, simulated mark, seed (if any), requested and applied sample
  rate, enabled channels, trigger, samples skipped before the trigger and start time.
- **FR-003**: The system MUST store and restore the capture status: closed, complete,
  lost positions, stopped by the memory limit and interrupted by a failure.
- **FR-004**: Saving the same session twice MUST produce byte-identical files, on every
  supported platform and independent of byte order or word size of the machine.
- **FR-005**: The file size MUST grow with the number of level changes (plus gaps and
  metadata), not with the number of samples or the number of idle channels.
- **FR-006**: The system MUST support the full range the storage core supports: no
  samples, one sample, 1 to the maximum number of channels, the maximum capture length
  and the maximum number of gaps.

**Safe writing**

- **FR-007**: The system MUST write a session atomically: the complete content is written
  to a temporary file next to the target, flushed to storage, and only then moved over
  the target, so that the target is at every moment either the complete old content or
  the complete new content.
- **FR-008**: A failed or cancelled save MUST leave an existing target file unchanged,
  MUST remove its temporary file, and MUST report a typed, actionable error.
- **FR-009**: A save MUST NOT begin writing until its inputs are validated (path,
  capture, description), and a path that cannot be written MUST fail before any data is
  written.
- **FR-010**: A temporary file left by an earlier crashed save MUST NOT prevent or
  corrupt a later save, and MUST be cleaned up or replaced.
- **FR-011**: The system MUST NOT fall back to a non-atomic write when an atomic one is
  not possible; it MUST report the failure instead.
- **FR-012**: The system MUST NOT overwrite or delete any file other than the target and
  its own temporary files, which are recognised by a strict name pattern tied to the target
  (this includes leftovers of earlier saves of the same target, removed only when stale).

**Safe reading**

- **FR-013**: The system MUST validate everything it reads: file identification, format
  version, section structure, sizes, counts, text encoding, checksums and the internal
  consistency of the capture; the capture MUST pass the storage core's own consistency
  rules before it is returned.
- **FR-014**: Damage anywhere in a file (truncation, any changed bit, appended bytes)
  MUST be detected and reported; a damaged file MUST NOT be loaded.
- **FR-015**: Every size and count read from a file MUST be checked against explicit
  limits and against the remaining file size before memory is allocated for it; loading
  MUST never allocate more than the configured memory budget and MUST NOT depend on a
  size claimed by the file for its allocation.
- **FR-016**: The loader MUST NOT panic, hang, recurse without bound or exhaust memory
  on any input; every failure is a typed error with a stable code and an English,
  actionable `detail`.
- **FR-017**: A file that is too large for the memory budget once loaded MUST be rejected
  with a typed memory-budget error before the data is read into memory.
- **FR-018**: The loader MUST distinguish and name these failures: not a session file,
  newer than supported, truncated, damaged (checksum), inconsistent content, too large
  for the budget, unreadable (permission, missing), cancelled.
- **FR-019**: A read MUST not be affected by the file changing while it is read: the
  result is either a correct session or a typed error.

**Marks that cannot be lost**

- **FR-020**: The simulated mark, the seed and the completeness information MUST be
  preserved by save and load, and a change to them inside a file MUST be detected as
  damage.
- **FR-021**: A loaded session MUST offer no way to clear the simulated mark or to turn an
  incomplete capture into a complete one.
- **FR-022**: A loaded interrupted or incomplete capture MUST stay incomplete, with its
  gaps and its reason.

**Format evolution**

- **FR-023**: The format MUST carry a version; the system MUST load every version it
  has ever written and MUST reject a newer major version with a message naming the found
  and the supported versions.
- **FR-024**: The file MUST consist of independently checked sections with identifiers;
  the capture and the description are required, and any number of optional sections MAY
  follow.
- **FR-025**: The system MUST keep unknown optional sections unchanged when a session is
  loaded and saved again, and MUST reject a file that contains an unknown section marked
  as required.
- **FR-026**: Fixture files written by each released version MUST be kept in the
  repository, and a test MUST load them on every build.
- **FR-027**: Section identifiers MUST be validated: duplicates, reserved identifiers and
  malformed identifiers are damage.

**Background operation**

- **FR-028**: Saving and loading MUST run in the background: the call returns at once,
  progress is observable, and the operation is cancellable and never blocks the UI
  thread.
- **FR-029**: Cancelling MUST stop the operation promptly and MUST leave no partial
  result: no temporary file, no change to an existing target, no partially loaded
  capture.
- **FR-030**: A capture that is still recording MUST be savable: the file holds a
  consistent prefix of the data recorded at that moment, is marked incomplete, and the
  recording is neither paused nor altered.
- **FR-031**: A fault in the worker of a save or load (including a panic) MUST be
  contained and reported as a typed error, without affecting the application or the
  capture in memory.
- **FR-032**: Saving and loading MUST report progress (fraction done) that never moves
  backwards, and MUST end with exactly one outcome.

**Quality and process**

- **FR-033**: The loader MUST be fuzzed or property-tested with malformed and boundary
  inputs, including truncations at every length and a bit flip at every position of
  representative files, and by a continuous fuzzing target.
- **FR-034**: All user-visible failures MUST have stable codes (in the `session.*`
  family, with storage and I/O errors passed through with context) and English details;
  the feature contains no UI text.
- **FR-035**: Log output MUST contain metadata only (sizes, counts, codes, durations) and
  MUST NOT contain signal data or the content of text fields.
- **FR-036**: Format behaviour (layout, versioning rules, limits, checksum use) MUST be
  documented in the repository so that other tools can read and write the format.

### Key Entities

- **Session**: the unit saved and loaded: one capture, its description, and a set of
  optional sections.
- **Capture**: the signals of one acquisition: channels, sample rate, transitions per
  channel, gaps, length and status (from the storage core).
- **Capture description**: the metadata of the acquisition (from the device layer),
  including the simulated mark and the seed.
- **Section**: an identified, individually checked part of the file; required or
  optional; unknown optional sections are kept as opaque data.
- **Format version**: the version of the file layout, with a major part that breaks
  compatibility and a minor part that does not.
- **Save operation / load operation**: a background activity with progress, cancel and
  exactly one final outcome.
- **Limits**: the explicit maxima (channels, transitions, gaps, sections, text length,
  file size, memory budget) a loader enforces before allocating.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: For at least 1,000 randomly generated captures (including empty, one-sample,
  maximum-channel, gapped and incomplete ones), save followed by load reproduces every
  query result and every metadata field exactly, with zero differences.
- **SC-002**: Saving the same session 100 times yields 100 byte-identical files, and the
  committed reference files are byte-identical when produced on Windows and on Debian.
- **SC-003**: With a failure injected at every step of a save over an existing file
  (at least 20 distinct injection points, plus 1,000 process kills at random moments),
  the previous file is intact and loadable in 100% of cases, and no partial file ever
  carries the target's name.
- **SC-004**: A valid file truncated at every length and a valid file with a single bit
  flipped at every position are rejected in 100% of cases, never loaded as valid, and
  never panic.
- **SC-005**: A continuous fuzzing run of at least 1,000,000 inputs produces no panic, no
  hang longer than 5 seconds and no allocation above the configured budget; the run is
  repeated in CI for a bounded time on every change to the format.
- **SC-006**: A file that declares sizes far beyond its real length (counts up to the
  largest representable value) is rejected without allocating more than 1 MiB beyond the
  size of the file.
- **SC-007**: A capture of 100 million samples on 16 channels with a typical signal saves
  and loads in under 10 seconds each on the reference machine, and the result for the
  same capture on a current Debian 13 CI runner is recorded as informational; the numbers
  are kept in a recorded baseline.
- **SC-008**: Starting a save or a load of any capture returns to the caller in under
  10 ms, and cancelling a running one finishes within 100 ms for a capture of any size.
- **SC-009**: Saving a capture while the virtual device is still recording it never
  pauses the recording for more than 10 ms and the file always loads as a valid,
  incomplete session.
- **SC-010**: In 100% of tests, the simulated mark, the seed and the completeness status
  survive any number of save and load cycles, and an edit of any of them inside a file is
  detected.
- **SC-011**: Every fixture file written by a released version loads to its recorded
  expected content on every build; a file with an unknown optional section survives a
  load and save cycle unchanged in 100% of tests.
- **SC-012**: The documentation of the format is sufficient for an independent reader to be
  written: a test reads and writes a file using only the documented rules, written
  separately from the implementation, and agrees with it on the committed fixtures.

## Assumptions

- The session file holds exactly one capture in this version; several captures in one file
  (a project) are a later extension through additional sections.
- Compression of sample data is not part of this item; the compactness comes from storing
  level changes rather than samples. A later minor version may add optional compression
  without breaking this one.
- Encryption, signing and access control of files are out of scope; checksums protect
  against damage, not against a deliberate attacker who can recompute them. A crafted
  but well-formed file can only produce a session that passes the consistency rules and
  stays within the budget.
- Periodic saving and recovery after a crash during a recording are policies of the
  application (roadmap item 006); this item provides the safe, background-capable save of
  a running capture they will use.
- Decoder settings, annotations, view state and notes are added by later items as optional
  sections; this item defines how sections work and stores none of them.
- The file name extension, the exact byte layout, the checksum algorithm and the text
  encoding are decisions for the plan; the requirements above fix only their observable
  properties.
- Import and export of other formats (sigrok `.sr`, CSV, VCD) are separate, later items.
- Reading of session files from other tools (PulseView) is not supported and not
  attempted; no code, file layout or text is reused from other projects.
- The memory budget is the one the storage core already defines and enforces; the loader
  uses it, it does not introduce its own policy.
- The supported operating systems are Windows 10/11 and Debian 13; behaviour is identical
  on both, and the reference machine for performance numbers is the maintainer's.
- Depends on roadmap item 002 (signal storage core: capture, snapshot, limits, status) and
  on item 004 (capture description with the simulated mark, seed and start time).
